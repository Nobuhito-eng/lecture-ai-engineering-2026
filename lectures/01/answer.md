## 演習・基礎：同じ質問を3回ずつ実行

### 方法

次の2問を、会話履歴を持たない独立した質問として各3回送った。質問文と回数を揃え、モデルだけを切り替えた。temperatureは明示指定せず、モデルの既定設定を使った。

1. 一般的な質問：「LoRAとは何ですか？」
2. 講座固有の質問：「AIE2026の講座の宿題にある『3レベル』とは何ですか？」（実際に送った句読点・括弧はJSONL内の `question` に保存）

```bash
uv run --frozen python -m scripts.day1_compare --models gemini-3.5-flash-lite gemini-3.8-flash
uv run --frozen python -m scripts.day1_compare --models gemini-3.1-flash-lite
```

各API呼び出しの終了後に15秒待ち、自動再試行は行わなかった。最初の比較で503が続いたため、失敗を残した上で、利用可能なモデル一覧にあった別モデルでも同じ6回を試した。

### 回答内容の違い

`gemini-3.5-flash-lite` では6回とも回答を得た。

- **LoRAの3回**：Low-Rank Adaptationという名称、元モデルを固定して小さな追加パラメータを学習するという説明は共通していた。「付箋」「メモ用紙」「アドオン」などの比喩、節の順序、画像生成AIやLLMの具体例、文章量が変わった。2回目には画像生成での使用について「ほぼ100%に近い確率」という強い表現もあり、根拠は回答内で示されていなかった。
- **講座固有の質問の3回**：1・2回目は、この講座を特定せず、一般的な「基礎・応用・発展」の説明を中心に返した。2回目には複数レベルを必須とする場合が多いという一般論も含まれた。3回目は、この講座の詳細を知らないと明示した上で一般論を説明した。同じ入力でも、不確実性の示し方と断定の強さが変わった。

正しい講座の定義は `data/glossary.json` の `homework-levels` と演習資料で確認した。区分は「基礎・実装・発展」であり、どれか1つに取り組めば完了する。モデルの一般論を、そのままこの講座のルールとして採用できないと分かった。用語集やスライド本文はAPIへ渡していない。

以下は成功した回答だけの値。入力・出力トークン数はAPIの `usage_metadata` から取得した。思考トークン数の未取得値は `null` のまま保存し、ゼロとはみなしていない。

|---|---:|---:|---:|---:|
| LoRA | 1 | 7 | 649 | 5.493 |
| LoRA | 2 | 7 | 672 | 3.521 |
| LoRA | 3 | 7 | 555 | 5.159 |

| 講座の3レベル | 3 | 21 | 318 | 17.102 |

同一質問では入力トークン数が一定だった一方、出力トークン数と経過時間は変わった。LoRAの経過時間中央値は5.159秒、講座固有の質問は13.947秒だった。後者は出力が短くても時間が長い例があり、回答の文字量・トークン数だけでは待ち時間を説明できない。

時間は `time.perf_counter()` で `generate_content` 呼び出し全体を測った。ネットワーク・接続・サーバー処理・回答の受信等を含み、最初のトークンまでの時間やモデル内部の計算時間だけを測った値ではない。15秒の待機は計測区間に含めていない。

503や404を「短時間で回答できた」とは評価せず、成功回答の速度表から除外した。別モデルの回答品質や成功時の速度・使用量を比較できなかったため、モデル間の優劣は結論づけない。

## 実装：会話履歴を保った追加質問

`app/ask.py` に `--chat` を追加した。従来の単発質問は維持している。

```bash
uv run --frozen python -m app.ask "LoRAとは何ですか？"
uv run --frozen python -m app.ask --chat
```

同じSDKのチャットを使い続け、利用者の質問とモデルの回答の両方を次の質問に渡す。空入力は送らず、`/exit`、`/quit`、入力終端で終了する。履歴は実行中だけ保持し、終了後は引き継がない。APIエラー時は説明を表示して次の入力を受け付ける。エラーの詳細は秘密情報を含む可能性があるため表示しない。

### 実APIでの確認

実際の `python -m app.ask --chat` を起動し、次の2問と `/exit` を標準入力から順に渡した。モデルの応答は差し替えていない。

| ターン | 入力の要点 | 実際の回答 | 入力 / 出力トークン |
|---|---|---|---:|
| 1 | 合言葉は「青い栞47」。覚えましただけ返す | 覚えました | 21 / 2 |
| 2 | 先ほどの合言葉をそのまま答える | 青い栞47 | 38 / 5 |

2問目の入力には合言葉を書いていない。直前に伝えた文字列を正しく返し、入力トークン数も増えた。プロセスは終了コード0で終了し、標準エラー出力は空だった。この1会話は長い対話やあらゆる内容での履歴保持を保証するものではない。

### APIを呼ばないテスト

既存分を含む21件が、Codespaces上で成功した（7.51秒）。Windowsローカルでも前の段階で21件の成功を確認済み。

追加テストでは実際のSDKの履歴処理を使い、モデル呼び出しだけをテスト用の応答に差し替えた。2回目の送信内容に最初の質問・最初の回答・追加質問が揃うこと、APIエラーになった質問が成功した履歴に混ざらないこと、空入力・終了・単発質問・使用量未取得時の表示等を確認した。テスト用応答をGeminiの実測結果としては扱っていない。

実APIで実行した4ファイルは、Windows側でテストしたコードの改行をLFに揃えたSHA-256と一致した。

## 計測と無料枠についての考察

- Googleの公式資料では、レート制限にはRPM（分あたりリクエスト数）、入力TPM（分あたりトークン数）、RPD（日あたりリクエスト数）があり、いずれかを超えると制限エラーになる。上限はプロジェクト・モデル・利用階層等に依存し、AI Studioで確認する必要がある。
- 今回の比較は呼び出し間隔を15秒空けたが、この間隔だけでTPMやRPDを含む全制限を避けられるとは限らない。アカウント固有の上限値は未確認で、課金設定は変更していない。
- 今回は429は観測せず、503と404を記録した。これを無料枠の上限到達の実証とはみなさず、失敗理由を混同しない。
- 比較では履歴を持たせず、会話モードとは分けた。履歴を保つと、今回も2問目の入力使用量が増えており、1回の応答だけでなく会話全体の入力使用量にも注意が必要だと考えた。
- 各条件3回のみで、モデルや質問の実行順も固定している。接続の再利用、時間帯、サーバー側の状態等の影響を分離しておらず、一般的な性能評価には不足する。複数モデルの成功回答を揃えた発展課題の比較は未完了として残す。

参考：[Gemini APIのレート制限](https://ai.google.dev/gemini-api/docs/rate-limits)（2026年10月20日確認）。
